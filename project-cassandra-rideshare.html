Effortless Scalability: Cassandra and AWS Powering Real-Time Rideshare Operations

September 2024 · 6 min read

Introduction

Imagine a rapidly growing rideshare company facing an influx of massive datasets. The company needs a robust database solution to efficiently manage and analyze high-volume, time-series data. The challenge: find a system that can handle large amounts of data quickly, stay running even if part of it fails, grow as the company grows, keep data secure, and not break the bank. Apache Cassandra on AWS is being considered as a solution.

The solution should handle large-scale time-series data efficiently, ensure always-on availability, scale seamlessly, implement strong security, perform well under high concurrency, and be cost-effective.

Solution Architecture

Choosing the Right Dataset

The NYC Yellow Taxi Trips dataset was chosen — collected by the NYC Taxi and Limousine Commission, it includes detailed trip information such as pickup/drop-off times, distances, and fare amounts. The dataset spans January to May 2022 and contains over 16 million records.

Efficient Data Handling

The dataset was partitioned by pickup date because time-series data is best handled by segmenting into manageable chunks based on time. Cassandra distributes data efficiently across nodes, enabling parallel processing and faster query responses.

Ensuring Availability and Resilience

A 6-node Cassandra cluster was set up on AWS EC2 instances distributed across three availability zones in us-east-1. This provides high availability (if one zone goes down, others continue), fault tolerance (handles an entire zone failure), improved performance (data processed closer to where it's needed), and easy scalability.

Replication for Resilience

A replication factor of 2 was chosen — each piece of data stored on two nodes. This provides data redundancy while keeping write performance efficient. The Network Topology Strategy ensures data is spread across availability zones.

Loading and Querying Data

The dataset was loaded at a rate of 6,500 rows per second using the COPY command, with Cassandra's sharding mechanism distributing data evenly across all nodes for parallel processing.

Security

Network security restricted EC2 access to specific IPs. User authentication was enabled with multiple roles. Specific permissions were assigned to limit access. Automated backups were set up via bash script, storing snapshots in Google Drive.

Performance Test

A NodeJS application was developed to interface with Cassandra, with Postman used to trigger queries. Three query types were tested:

SELECT MAX(trip_distance) FROM nyc_taxi_data.yellow_taxi_trips WHERE pickup_date='2022-01-01';
SELECT AVG(total_amount) FROM nyc_taxi_data.yellow_taxi_trips WHERE pickup_date='2022-01-01';
SELECT COUNT(*) FROM nyc_taxi_data.yellow_taxi_trips WHERE pickup_date='2022-01-01';

Recommendations

  • Use a Multi-Node Cluster for environments with high concurrency and large data volumes.
  • Implement Time-Based Partitioning to distribute load efficiently across nodes.
  • Handle Geographically Disparate Requests using Cassandra's ability to route to the nearest node, and consider CDNs for frequently accessed data.
